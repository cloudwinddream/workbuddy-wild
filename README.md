# WorkBuddy Wild

**WorkBuddy/CodeBuddy + TraeWork 账号的 OpenAI 兼容代理 + 自动签到 Windows 托盘工具。**

双平台支持：聚合多个 WorkBuddy 和/或 TraeWork 账号，提供统一 OpenAI 兼容 API。
支持模型前缀区分（`workbuddy/<model>`、`traework/<model>`），自动路由到对应上游。

面向普通用户：**下载即用**，一个 exe 搞定账号登录、自动签到、积分查看、模型路由，为你的 AI 客户端（pi、Claude Code、Cursor 等）提供 OpenAI 兼容接口。

> 本项目源于两个原始项目，在其基础上重做为 Windows 双平台托盘应用：
> - [Sliverkiss/workbuddy2api](https://github.com/Sliverkiss/workbuddy2api) — WorkBuddy/CodeBuddy 上游
> - [Sliverkiss/traework2api](https://github.com/Sliverkiss/traework2api) — TraeWork SOLO 上游
> 
> 开发者/高级配置见 [docs/DEVELOPMENT.md](docs/DEVELOPMENT.md)。

### v0.5.7（2026-09-30）
- **修复 TraeWork 多账号签到仍全失败（9074）** —— 单变量实测定位，两处真问题
  - **纠正 v0.5.6 的结论**：v0.5.6 认为"9074 = 设备号 + 请求体"，方向对了一半。
    实测表明**请求体不是必要条件**：
    - 随机设备号 + `{"req_source":1}` → 9074
    - 随机设备号 + `{}` → **成功**（服务端在体为空时跳过设备校验）
    - 真实设备号 + `{"req_source":1}` → 成功
    - 真实设备号 + `{}` → 成功（9095 今日已签）
    → 决定因素只有**设备号**。既然桌面端真实行为带 `req_source`，两者都要对。
  - **真因 1：登录时设备号没取到真实值**。`Start()` 里虽然调了
    `ReadClientDeviceID()`，但 9074 在修复后依然复现，说明该调用实际返回空
    （回退成随机值）。现改为：
    - `Start(client, statePath, deviceID)` 新增第三参，由调用方显式传入
    - 新增 `ListClientDeviceIDs()` / `NextClientDeviceID(idx)`：扫描**所有**
      客户端数据目录，多账号按序分配**不同**的真实设备号（避开"同设备一天只能签一个账号"）
    - 日志明确打印取到的设备号前缀与来源路径，取不到时给出显著警告
  - **真因 2：签到成功却被判失败（新发现的独立 bug）**。
    判定字段是 `did_checked_in`，而原实现只读 `checked_in`：
    ```
    签到成功响应：{"checked_in":false,"did_checked_in":true,...}
    ```
    `checked_in` 表示"用户当前处于签到会话"，对 API 调用方**恒为 false**。
    旧实现因此每次签到都误判失败并无谓重试。新增 `CheckinStatusFull()` 同时返回两者。
  - **9074 语义修正**：不再当"高峰限流"。`ErrCheckinRateLimited.IsRateLimited()`
    由 `true` 改为 `false` —— 设备未注册时重试**永远不会成功**，
    原先的指数退避（8s→16s→32s）纯属浪费时间。现在一次判定、立即报错。
    单账号签到耗时从最坏 ~60s 降到 ~1s，并去掉了"稍后自动重试"的空头承诺。
  - 移除 `backoffDelay()`、`Client.CheckinRetry/CheckinMaxTry` 等已失效机制
  - 测试重写：删除 4 个"限流应重试"的错误用例，新增
    `TestDailyCheckinAcceptsDidCheckedIn`（锁定 did_checked_in 语义）、
    `TestCheckinClaimDeviceRejectedIsNotRateLimit`（锁定 9074 不可重试）等
  - **实测结果**：两个真实账号修复设备号后，`claim` 一次成功，9074 归零

### v0.5.6（2026-09-30）
- **修复 TraeWork 签到恒失败（9074）** —— 根因是**设备号 + 请求体**两处，与「限流」无关
  - **纠正认知**：9074 的文案「当前参与用户太多」是**误导**。它不是限流，
    重试再多次也没用（v0.5.4 把重试窗口扩到 3.5 小时的方向是错的）
  - **真因 1：设备号**。服务端按「注册指纹」校验 `x-device-id`，
    必须是**客户端在服务器上真实注册过的**设备号。原实现用 `randHex(16)` 随机生成，
    必然被拒。
    - 修复：登录时从本机 TraeWork 客户端的 `storage.json` 读取真实设备号
      （明文写在键名上：`iCubeAuthInfo://icube-dc:4484256452647802`）
    - 候选目录覆盖 `TRAE SOLO CN` / `Trae CN` / `.trae-cn` 等
    - 读不到时回退随机值并记日志（其它功能不受影响，仅签到会失败）
    - 刻意**不采用** UUID 形式的 `telemetry.devDeviceId`
      —— 资料明确它不被识别为注册设备，用了会被更严格限流
  - **真因 2：请求体**。`claim` 原发送空对象 `{}`，被拒为 9074
    （与设备失败共用同一业务码，极易误判）。改为 `{"req_source":1}`
  - 新增 `internal/login_trae/device.go` + 5 个用例（键名提取、忽略 UUID、
    拒绝过短、目录缺失、临时目录读取）
  - **实测**：真实环境下成功读到设备号 `4484256452647802`

- ⚠️ **上游限制：签到额度按「设备」计算，不是按账号**
  - 原文：「当前**设备**今日已经签到，请明日再来哦~」
  - N 个账号每天各签一次，需要 **N 个不同的设备号**（即 N 台装过客户端的机器）
  - 单设备下多账号签到，只有第一个能成功 —— 这是上游设计，非程序缺陷

### v0.5.4（2026-09-30）
- **修复 TraeWork 签到失败后不会真正重试**（「稍后自动重试」是空头承诺）
  - 现象：签到提示「上游繁忙，稍后自动重试」，但之后**再也没重试过**，
    要等到下一个定时点（可能间隔数小时）
  - 根因：限流耗尽后只设置了 `CheckinResult.Retryable = true`，
    而**该字段没有任何代码消费** —— 调度器 `Run` 循环只按固定的
    `checkin_times` 唤醒，不会因重试请求而提前唤醒
  - 修复：调度器新增**独立的延迟重试队列**
    - 限流耗尽 → 安排 10 分钟后重试；未成功则 20 / 30 / 40 / 50 / 60 分钟递增
    - `Run` 循环唤醒时刻取「下次定时点」与「最近重试时刻」的**较早者**
    - 重试只针对失败账号，不影响其它账号
    - 签到成功后（`clearRetry`）立即清除待重试状态
    - 跨天自动重置计数；单日上限 6 次，防止上游长期异常时无限重试
  - 效果：**重试覆盖窗口从 58 秒扩展到 3.5 小时**，足以跨过正常高峰
  - 新增 `internal/scheduler/retry_test.go`（6 个用例覆盖调度、退避、上限、跨天重置、
    账号隔离、成功后清除）

### v0.5.3（2026-09-29）
- **修复 TraeWork 积分口径（最终版，基于真实抓包确认）**
  - 根因：此前调用的 `ide_user_ent_usage` 是 **IDE 客户端专用**接口，网页端不调用，
    字段口径也不同（其 `credits_limit` 是每包上限，累加自然虚高）。
  - 真实接口是 **`POST /trae/api/v2/pay/user_current_entitlement_list`**，
    响应里的 `usage_summary` 给出权威口径：
    ```
    total_amount    = 4050     累计发放
    consumed_amount = 3751.3   累计消耗
    剩余 = 4050 - 3751.3 = 298.7   ← 与官网个人中心一致
    ```
  - 现在**首选 `usage_summary` 相减**；并以逐包 `credits_limit - usage.credits_amount`
    求和作为兜底与交叉验证（两种算法在真实数据上都得 298.7）。
  - 修正一处语义误判：`usage: {}` 表示该包**未被使用**（剩余 = 全额上限），
    而非"无法判断"——此前会跳过该包导致余额虚低。真实响应里最新签到包正是此形态。
  - 用**真实抓包响应**新增 4 个测试（`real_response_test.go`），锁定该口径。

### v0.5.2（2026-09-29）
- **修复 TraeWork 积分仍不正确（显示 150）**：v0.5.1 在权益包解析不出余额时，回退读取签到接口的 `credits` 字段，并假定其语义是「当前可用积分」——**该假定是错的**
  - 实测证据：该字段在 16 次采样中**恒为 150**，不随天数与消耗变化（对照 WorkBuddy 的余额有 2100/2200/2300/2400/2500 五种取值）；它是**签到奖励固定值**，不是余额

  - 收紧了字段名白名单：移除裸 `credits` / `total` / `quota` 等宽泛名，避免误匹配到签到奖励值等无关字段

  - 新增 5 个回归用例：禁止回退签到接口、忽略裸 `credits`、忽略裸 `credits/used` 减法、部分包不可解析时跳过

## 它解决什么问题

- WorkBuddy/CodeBuddy 和 TraeWork 账号的对话额度有限，多个账号可以共享/轮流使用
- 本项目把多个账号聚合成一个 **OpenAI 兼容 API**，按可选的策略（优先积分 / 优先过期 / 负载均衡）挑选账号、自动刷新 token、错误自动冷却
- 每天**自动签到**领额度，面板随时看积分、签到状态
- 全部在一个后台托盘程序里，无需任何编程环境

## 快速开始（普通用户）

1. **下载**：从 [Releases](https://github.com/sddvcm/workbuddy-wild/releases) 下载最新版 `workbuddy-wild-windows-amd64.zip`，解压后双击 `workbuddy-wild.exe`
2. 稍等片刻会弹出提示框，显示 **OpenAI 兼容 API 地址**（默认 `http://127.0.0.1:7863`）——记住它，关掉即可
3. 右下角出现绿色 W 托盘图标，**单击 / 双击 / 右击** 都能打开管理面板
4. **添加账号**：面板点"＋ 添加账号"→ 选择 WorkBuddy 或 TraeWork → 自动打开无痕浏览器 → 登录对应平台 → 自动写入凭证并立即签到
5. **配置客户端**：把你的 AI 客户端指向
   ```
   Base URL: http://127.0.0.1:7863/v1
   API Key:  WorkBuddy2API   （面板"API-Key"处可随时修改）
   ```
6. 面板里还能：改自动签到时间（默认每天 09:00、21:00，支持分钟）、看签到状态、刷新积分、改监听地址、开机自启、查看日志、退出

> 首次运行自动生成 `config.json`（默认监听 `127.0.0.1:7863`）。程序常驻托盘，双击 exe 只是唤起/提示，主界面通过托盘图标打开。

## 与原始项目的区别

| | 原始 workbuddy2api | WorkBuddy Wild |
|---|---|---|
| 使用方式 | 命令行 + 脚本 + Docker，需安装 Go/Python/Docker | **单个 exe 双击即用**，零依赖 |
| 界面 | 无（纯 HTTP 服务） | **系统托盘管理面板**（添加账号/签到/积分/配置） |
| 登录 | Bash 脚本 + 手动复制粘贴授权 URL | 一键拉起**无痕浏览器**，自动完成登录轮询 |
| 签到 | 手动跑脚本 / 固定 9·21 点 | 面板**可视配置签到时间（支持分钟）**，即时生效 |
| 账号状态 | 无 | 面板实时展示**积分/签到记录/冷却状态**，单账号手动签到/刷新 |
| 监听配置 | 改配置文件重启 | 面板下拉选择 + **热切换**（不重启） |
| 日志 | 控制台 | 写 `data/app.log`，面板一键记事本打开 |
| 构建 | Linux 优先 | Windows 单文件，GitHub Actions 自动发布 |

## 功能清单

- ✅ OpenAI 兼容代理：`/v1/models`、`/v1/chat/completions`（流式/非流式）、`/status`、`/healthz`
- ✅ 双平台支持：同时接入 WorkBuddy（CodeBuddy）和 TraeWork 账号，模型 ID 以 `workbuddy/` 或 `traework/` 前缀路由
- ✅ **三种选号策略**：优先积分（默认）/ 优先过期 / 负载均衡，面板下拉切换即生效
- ✅ **账号调用标识**：实时显示「调用中」/「最近用过」，正在调用的账号自动置顶
- ✅ **双栏面板**：左账号列表（内部滚动）/ 右设置栏，账号再多也不挤
- ✅ 托盘面板：添加账号（无痕浏览器）、自动签到时间配置、签到状态、积分实时刷新
- ✅ API 监听主机/端口可改（`127.0.0.1` 本机 / `0.0.0.0` 全部 / 自定义），热切换
- ✅ 账号凭证 DPAPI 加密落盘、日志自动轮转、开机自启、面板位置记忆
- ✅ 开机自启（注册表 Run 键）、查看日志、退出

## 客户端兼容性（pi / Claude Code 等）

兼容标准 OpenAI 格式（`/v1/chat/completions`）。特别的兼容处理：

- **模型 ID 必须带平台前缀**：`workbuddy/<model>` 或 `traework/<model>`。
  例如 `workbuddy/hy3`、`workbuddy/deepseek-v4-pro`、`traework/DeepSeek-V4-Flash`。
  不带前缀的模型名会返回 400 错误。
- **`developer` 角色自动转换**：pi 等客户端对推理模型会用 `role=developer` 发送系统提示词。
  两条上游管道均已自动将 `developer` 归一化为 `system`，避免内容过滤误杀。

### 获取完整模型列表

所有可用模型通过标准 OpenAI `/v1/models` 端点获取，直接请求：

```bash
curl http://127.0.0.1:7863/v1/models -H "Authorization: Bearer WorkBuddy2API"
```

返回的列表中每模型都带 `workbuddy/` 或 `traework/` 前缀。
可以让 agent 先拉取模型列表，再依据下面的配置示例自动生成 models.json。

### pi 配置示例

编辑 `C:\Users\<用户名>\.pi\agent\models.json`，在 `providers` 中加入：

```jsonc
"workbuddy-wild": {
  "name": "WorkBuddy-Wild",
  "api": "openai-completions",
  "baseUrl": "http://127.0.0.1:7863/v1",
  "apiKey": "WorkBuddy2API",
  "models": [
    {
      "id": "workbuddy/hy3",
      "name": "hy3 (WorkBuddy)",
      "reasoning": true,
      "input": ["text"],
      "contextWindow": 192000,
      "maxTokens": 64000,
      "compat": { "maxTokensField": "max_tokens" }
    },
    {
      "id": "traework/DeepSeek-V4-Flash",
      "name": "DeepSeek V4 Flash (TraeWork)",
      "reasoning": true,
      "input": ["text"],
      "contextWindow": 1000000,
      "maxTokens": 50000,
      "compat": {
        "thinkingFormat": "deepseek",
        "supportsReasoningEffort": true,
        "maxTokensField": "max_tokens"
      }
    }
  ]
}
```

> 模型 ID 必须按 `workbuddy/` 或 `traework/` 前缀，否则请求被拒。
> 名称建议标注来源 `(WorkBuddy)` / `(TraeWork)` 以便区分同名模型。
> 建议只配置实际要用的模型，避免列表过长。

## 常见问题

**提示框显示的地址访问不了？**
检查是否改过监听地址：面板"API 监听"里看当前地址；或看 `data\app.log`（面板"查看日志"）。

**添加账号时浏览器没打开？**
面板登录框里有"复制链接"，可手动在浏览器（无痕窗口）打开完成登录。

**签到时间改了没生效？**
时间修改即写回 `config.json` 并立即生效，无需重启。

**Windows 提示“未知发布者”或报毒？**

本工具没有数字签名，因此可能会被 Windows 安全中心或杀毒软件拦截。如果报毒，请将本工具添加到排除项：

设置 → 更新和安全 → Windows 安全中心 → 打开 Windows 安全中心 → 病毒和威胁防护 → “病毒和威胁防护”设置/管理设置 → 排除项/添加或删除排除项 → 添加排除项（文件或文件夹），把 exe 或所在目录加进去。

如果对本仓库发布包不放心，可以自行基于源码构建（见开发文档）。

**TraeWork 多账号自动签到失败**

TraeWork有风控机制，无法确保多账号能可靠自动签到，这种情况建议使用客户端手动签到，登出客户端重新用另一账号登录即可签到。本工具的 API 转换功能不受影响。
